# 游戏效果入口核查（2026-09-25）

基准：源码 `3e89c330cece540054703f120318fc624ae7a5f7`，已部署DLL0.4.0/HKSv8。只读源码与本地配置，无游戏操作。

## 当前静态事实

- `src/forms.rs::Selector::route` 已支持自动形态的本体SpEffect出现边沿和优先级选择，但解除只接受外部 `Input.revert`，没有解除效果配置。
- `Config::validate` 强制默认形态为manual，不能仅把唯一c0010的trigger改为automatic。正式自动入口需要调整这项限制，并明确无调试按键时的配置约束。
- 安装配置仍是manual且未设置实际SpEffect ID，不能声称当前安装已完成手柄变身入口。
- `native.rs::update` 直接读取F6/F7，不存在调试热键开关；当前键盘边沿与后续效果路由应分开。
- `NativeBackend::sample_effects` 只扫描 `main_player`，即保留的玩家本体；不扫描受控兽体。若解除效果由兽体动作施加，仅检查本体不能覆盖该来源。
- 现有 `Identity::resolve` 和 `validate_session` 可验证归属，但清理退休队列接管后禁止再解析旧兽体。扩展效果读取必须遵守这个生命周期。
- 现有采样间隔100ms，不保证捕获仅存在一帧的动画效果。应使用可被观察的标记效果，或另行明确短脉冲捕获需求；不可把轮询描述为逐个动画通知的无损接收。

## 当前结论与边界

用户澄清的是正式操作方案，不应继续诊断F6/F7硬件故障。正式链路应为游戏动作/动画施加标记效果，再由已验证生命周期处理进入/解除。效果检测代码、参数效果行、实际施加该效果的动作资源，是三个不同接入环节。

本轮先形成增量Spec，等待用户选择双效果或单效果切换并提供/决定效果ID。尚未改DLL、HKS、游戏配置、参数或动画；不得关闭现有唯一可用入口后声称手柄接入完成。

后续用户已确认双效果、ID自定义；正式依据为spec-effect-controls.md@1.0。0.4.1实现补齐上述入口，未接线真实效果ID和游戏动作，游戏退出前不安装。
