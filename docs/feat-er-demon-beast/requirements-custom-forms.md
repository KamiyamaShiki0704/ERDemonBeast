# 多形态自定义需求

## 用户原意与实施顺序

用户同意继续真实魔兽最小形态阶段，同时要求该阶段完成后支持：根据不同 SpEffect 切换不同 ID 的形态；自定义每个形态存在时间；-1 表示无限、仅手动解除；出招逻辑和按键可以沿用玩家 c0000 的规则。

这些是后续扩展目标，当前 0.2.1 不宣称已支持。当前正式 Spec 1.0 的固定 15 秒和六组 Probe 保持原有含义。本文件为需求输入，不作为已确认的新 Build 规格。

## 已明确需要的能力

1. 可以定义多个形态，每个形态关联不同的 SpEffect 和角色身份，而非固定只使用一个兽体。
2. 每个形态具有独立的持续时间；有限时间到期还原，-1 无自动到期，仅手动解除变身。
3. 可以沿用玩家习惯的按键和出招规则，并驱动当前形态执行相应动作。
4. 后续配置能力以真实魔兽最小形态完成为前序；资源接入阶段应保留扩展空间。

## 用户已确认的两项语义

用户对两项问题分别回复：

- “两种都支持，每个形态分别配置”：同时支持 SpEffect 自动触发进入/切换，以及 SpEffect 选定形态后按键触发；按形态配置。
- “两种模式都预留，先实现输入与招式映射”：先实现玩家语义输入与招式映射，完整 c0000 动作脚本复用保留模式扩展点，不能宣称该模式已可运行。

这两项需求语义已经确认，无需重复询问。具体阶段的完整 Spec/Probe 仍需明确动作子集及验收阈值。

## 建议的默认行为，待纳入后续 Spec

| 场景 | 建议语义 |
|---|---|
| 持续时间起点 | 从目标形态成功受控开始计时，加载等待不消耗持续时间 |
| 无限时长 | 正常有效场景下不因时间或触发 SpEffect 自然消失而自动还原；手动解除有效。显式切换形态与异常中断另行定义 |
| 有限时长 | 按当前形态配置到期还原，手动解除可提前结束 |
| 持续 SpEffect 与解除 | 手动解除或到期后，同一次持续效果不得立即再次触发变身；必须定义明确的再次触发条件 |
| 多个匹配效果 | 依据明确的形态优先级选择唯一结果；冲突配置不能凭扫描顺序随机选择 |
| 活动中切换 | 旧形态完成释放后才接管新形态，全程至多一个受控兽体；新形态失败时回到可操控本体 |
| 未适配动作 | 明确报告该动作不受支持，不向任意角色强行发送不兼容的玩家动作 |
| 角色身份 | 每个形态应具备匹配的外形、动作、行为及参数，只有角色 ID 不保证可玩 |

## 候选验收场景

此表用于下一轮具体 Spec/Probe 的输入，不代表已通过或已确认全部阈值。

| 场景 | 输入与预期 |
|---|---|
| 形态选择 | 使用两种已适配形态，分别施加对应效果并执行所选触发方式，得到对应且唯一的形态 |
| 多效果 | 同时满足两种效果，按确认的优先级得到稳定结果 |
| 独立时长 | 两种形态分别配置短、长持续时间，从各自进入成功起正确计时和还原 |
| 无限 | 配置 -1；建议观测 60 秒且移除触发效果，保持形态，随后手动解除；有限观测只证明该窗口内无自动到期 |
| 防止自动重进 | 保持触发效果存在，手动解除或到期后观察，不因同一持续效果马上再次进入 |
| 切换与失败 | 在形态 A 中请求 B；确认不会同时拥有两个受控兽体；B 不可用时恢复本体 |
| 玩家规则 | 使用已确认的输入方案分别检查轻击、重击、蓄力/连段中本阶段纳入的子集，确认动作、时序、命中与返回状态 |

进入/恢复时限、计时容差、按键与动作子集、冲突优先级、再次触发条件、异常中断范围，需在后续具体 Spec/Probe 中明确。已有 3 秒恢复等标准可作为候选沿用，不能用本需求记录悄悄改写既有契约。
